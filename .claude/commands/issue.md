ユーザーの依頼「$ARGUMENTS」から Issue を作成してください。

## 1. 種別を決める

- `feature`: 新機能・既存機能の改善・ドキュメント改善
- `bug`: 不具合・想定外動作・回帰
- `experiment`: AI・アルゴリズム・性能評価など結果を比較して判断する作業

## 2. 雛形を取得する

ラベルを自分で書かず、必ず正本から取得する。

```bash
bash .claude/scripts/issue-form.sh skeleton <種別>
```

標準出力が本文の雛形、標準エラーが title の接頭辞・必須ラベル・選択肢。

## 3. 形式のルール

- 見出しは `### <ラベル>` のみ。`#` と `##` を使わない
- ラベルの文言と順序を雛形から変えない。ラベルを訳したり言い換えたりしない
- 見出しの下は1行空けて本文を書く
- title は接頭辞を付ける（例: `[Feature] カメラ切断時の自動再接続`）
- 選択肢のある項目は、提示された値をそのまま1つ選ぶ。新しい値を作らない
- 任意項目に書くことがなければ `_No response_` と記載し、見出しは残す

## 4. 分量のルール

**必要なことだけを書く。読み手が判断できる最小限にする。**

| 項目 | 目安 |
|---|---|
| 目的 | 1〜2文 |
| 背景・課題 / 現象 | 箇条書き3項目以内、または3文以内 |
| 変更内容 | 箇条書き。1項目1行 |
| 完了条件 / 成功条件 | 判定可能なチェックボックス。7項目以内 |
| 補足 | 関連 Issue や資料のリンクのみ |
| 本文全体 | 60行以内 |

書かないこと。

- 調査の経緯、検討の過程、試行錯誤の記録。必要ならコメントへ書く
- 他の項目で既に述べた内容の繰り返し
- まだ決まっていないことの推測
- 長いログ、コマンド出力、コード全文。リンクか抜粋にする
- 前置きや挨拶

完了条件は判定可能にする。「改善する」「良くする」「精度を上げる」は使わない。
Experiment の成功条件は、結果を見る前に数値で書く。

## 5. 情報が足りないとき

勝手に埋めない。`【要確認】` を付けてユーザーに質問し、答えを得てから作成する。
作業範囲が大きすぎる場合は Issue の分割案を出す。

顧客固有の要求を含む場合は `/customer-request` の二段階分類を行い、対象Componentと実装分類を `変更内容` に1行ずつ記載する。

## 6. 検証してから作成する

本文をファイルへ書き、形式を検証する。

```bash
bash .claude/scripts/issue-form.sh check <種別> <ファイル>
```

`OK` になるまで作成しない。確認後、ユーザーの承認を得て作成する。

```bash
gh issue create --repo MirumeAI/<repository> --title "<接頭辞><要約>" --body-file <ファイル>
```

発行された番号を報告する。Issue 番号が確定するまで Branch は作らない。
